## 第六轮：额度两大失效（2026-07-20 第四批，提交 `ac6fa58a`）

用户报「abort 的轮完全不计费、free 档 $0.3 形同虚设」，并怀疑中途封顶同样失效。实测两条都成立，
且第二条比怀疑的更彻底——**整条事件订阅链路从未收到过任何消息事件**。

### 实测锚定的两个根因

| # | 现象 | 根因 | 证据 |
|---|---|---|---|
| 1 | 中途封顶从未生效（**不分单消息轮 / 多步骤轮**） | 订阅打的是不带 `directory` 的 `GET /event`，而会话建在 `outputs/<ws>/` 子目录 → 只收到 `server.*` 心跳 | 裸 curl 对照抓包：`/event` 267 字节全是心跳；`/global/event` 同一轮 44108 字节、含 6 条 `message.updated` + 26 条 `message.part.delta` |
| 2 | abort 的轮零计费 | opencode 对被 abort 的消息记 `cost=0/tokens=0`（`MessageAbortedError`），`session.cost` 增量为 0 | 修前实测：跑 12s 后 abort，`quota.json` 从 `0.04142377` 一字未动 |

**关键佐证**：上游 one-api 对被 abort 的请求**照常全额扣费**——abort 后仍记 `ElapsedTime:51600ms`、
`CompletionTokens:2063`。即用户实打实花了钱，网关一分没记。

原以为"中途封顶至少对多步骤轮有效"（每步完成有真实 cost）——**这个假设也是错的**，因为循环压根收不到事件。

### 修法：网关侧估算兜底（未走 one-api 取账）

**为什么不用 one-api 的真实账**：① 所有用户容器共用一个 token（`OC_GATEWAY_KEY`），one-api 的日志
按 token 归账，**无法按用户拆分**；② 单条长请求 one-api 也要等请求结束才落账，救不了"中途封顶"这个
必须在轮内实时判断的场景；③ 现存 `model ratio not found: deepseek-v4-pro` 使其按 30× 兜底计费，账本身是错的。

- 订阅换 `/global/event`（事件外层包 `{directory, project, payload}`，拆包后沿用原过滤）；
- `perMsg`/`partMeta` 按流式 delta 实时累计每步输出 token 估算（中文 0.7/字、其余 0.35/字符，取向宁可高估）
  \+ 上一步实测的输入侧真实成本（新会话缺省 15k tokens，`OC_EST_INPUT_TOKENS` 可覆盖）；
- 结算 = `session.cost` 真实增量 + `cost=0` 消息的估算；**估算前先查 opencode 权威消息状态**，
  正常完成的绝不叠加（防事件竞态双重计费）；
- `gracefulExit` 与主循环结算用 `job.settled` **同步占坑**互斥；
- 附带修复：**流式直播复活**（此前前端只在轮末收到 `final`，整轮无字）。

### 复审发现并已修的自引入缺陷

复审 agent 报 7 条，其中 1 HIGH 已修，另修了 3 条中低危：

| 严重度 | 问题 | 修法 |
|---|---|---|
| HIGH | `gracefulExit` 不检查 `job.settled`、且自己的置位在 `await` 之后 → 与主循环结算**双向竞态双记** | check-and-set 前移到一切 await 之前；失败回滚 settled；`cost0` 未读到的刚起步轮跳过 |
| MED | 上一轮 abort 消息的迟到收尾事件被本轮收编 → 重复估算 | 按 `info.time.created >= jobT0` 过滤 |
| MED | 事件流异常死亡被 `catch(()=>{})` 静默吞掉 | 打 warn 日志（**上次这条链路就是无声死掉才拖到现在**） |
| LOW | 每条 delta 都同步读盘（`quotaUsedLive`）；`m.real = info.cost \|\| 0` 会把已知成本打回 0 | 封顶判断节流 250ms；改 `Math.max` |
