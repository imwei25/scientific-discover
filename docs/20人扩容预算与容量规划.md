# 扩容预算与容量规划：20 人并行 / 200 总用户

> 生成日期：2026-07-17。目标规模：**注册用户 ~200 人，同时在线并行干活（跑 Python / md→PDF 等）~20 人**。价格为阿里云官网价格页「中国（香港）」地域**目录价**（官方注明非实时、不含个人优惠，下单以 ECS 购买页实际报价为准，通常只会更便宜）。大模型 API 开支不在本预算内。
>
> 200 总用户对 CPU/内存**没有影响**（停止的容器占 0 内存，manager 按需拉起，`WARM_CAP` 控制同时运行数）；影响的是**磁盘容量**与**备份策略**，见 §6。

## 1. 现状

- 生产服务器：阿里云香港 `ecs.e-c1m2.large`（经济型 e，2 核 4G，共享 CPU），40G 系统盘，公网 IP `47.86.27.60`。
- 该规格目录价：包月 ¥125.8，年付折合 ¥106.9/月。
- 架构：Caddy(TLS) + manager.mjs 按需拉起每用户 Docker 容器；对公网仅开 22（安全组限 IP）/80/443。
- **结论先行：现机无论如何撑不了 20 人**——20 个用户容器空闲内存就要 ~5GB，4G 机器直接 OOM，与"卡不卡"无关。

## 2. 容量测算依据（2026-07-16 在现机实测）

- 每用户容器空闲驻留 ~245MB 内存；干活（md→PDF / 跑 Python）峰值再加 ~200–300MB。
- 重活（pandoc 转 PDF、Python 脚本）基本是**单核吃满约 4 秒**的突发型负载。
- 2 核机实测：并发 N=2 时吞吐即饱和（~0.43 次/秒）；N=4 延迟 2.9 倍、N=10 延迟 5.7 倍，纯 CPU 瓶颈，全程零失败零 OOM。
- 由此外推：**约 1 vCPU 支撑 1 个并行重任务不降速**；内存下限 = 20×245MB + 宿主组件 ≈ 6GB 空闲 + 干活峰值 → **16GB 起步**。

## 6. 200 总用户的存储账与备份策略

**磁盘怎么算的**：

- 每用户数据 = uploads + outputs + ocdata（OpenCode 会话）三个卷，受档位配额约束（现行 free=1GB、plus=4GB 存储上限）。
- 200 人若多数为 free 档：配额上限总和 ≈ 200GB+（plus 用户每人再多 3GB）。实际占用通常只有上限的 2–5 成，但容量规划要按"接近上限"留量。
- 系统 + Docker 镜像 + one-api 等固定开销约 25–30GB。
- ESSD Entry ¥0.35/GB/月，且**支持在线扩容不停机**——所以策略是"起步够用、按 `df` 增长再扩"，不必一步到位：方案 B 起步 300GB，方案 A 起步 500GB。

**备份必须改（200 人规模的隐形炸弹）**：

- 现行 `backup.sh` 是本地 7 天轮转——200 人数据 tar 出 7 份放同一块盘，备份占用会是数据本身的数倍，盘买多大都会被吃掉，而且备份和数据同盘等于没有容灾。
- 改法：本地只留 1–2 天，历史份推 **OSS**（香港标准型约 ¥0.15/GB/月，低频/归档更便宜），用 `ossutil` 或挂生命周期规则自动过期。预算表中的"OSS 异地备份"即按此估。
- 另建议开系统盘**自动快照**（保留 3–7 天，快照按增量计费，几十 GB 系统盘每月约 ¥5–15），防误操作系统级回滚。

**200 用户的其他影响（都不构成瓶颈）**：

- 停止的容器不占内存，`WARM_CAP=20` 即同时运行上限；manager 按需拉起、闲置回收的机制天然适配"200 注册、20 并发"。
- `users/*.env` 200 个文件、compose 200 个 service 定义均无压力；用户增删已有 `user-add/del.sh` 和 /admin 面板。
- 图形验证码 + fail2ban 在 200 用户下照常工作；审计日志建议加 logrotate。

## 7. 推荐路径

1. **先上方案 B（约 ¥900/月）**：重活是秒级突发，20 人同时点"转 PDF"的概率很低，B 的"卡"多数时候感知不到。
2. 真觉得慢再**原地升配**到方案 A：u1 家族内升配补差价即可，docker 卷原地保留、不搬数据、停机几分钟。
3. 升配后的软件侧改动：`WARM_CAP` 调到 20；每容器 CPU 限额 1.5 核可保持不变。
4. 软件层开支为零：Caddy、fail2ban、one-api、manager 全是自建免费组件。

## 8. 附：当前安全面（与扩容无关但同期核查）

- 对公网仅 22/80/443；22 由安全组限源 IP；manager(8090)、one-api(3010)、Caddy 管理口(2019) 均只绑回环。
- fail2ban 在跑（caddy-login + sshd 两个 jail）；登录有图形验证码 + 失败延迟；每日费用额度封顶经济损失。
- 已知缺口：HTTP 层无限流（Caddy 标准构建无 rate_limit 模块、manager 无限流逻辑），单机高频骚扰可拖卡小机器；大流量 DDoS 仅有阿里云免费基础清洗，超阈值进黑洞——对 10–20 人内部工具建议接受该风险，不值得买高防。
