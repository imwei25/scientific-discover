## 核心能力（一）：验证 AI 的输出

我们反复遇到同一类问题：**AI 给出的答案推理严密、措辞自信、而且是错的。** 三个真实案例，都发生在这个项目上，面试时可以展开聊：

- 排查中文图表乱码，AI 断言「matplotlib 支持逐字形回退，字体栈这样写没问题」，逻辑自洽并引用了版本特性。实际跑一次：**28 个字全是豆腐块**，机制与它所说的完全不同。
- 排查告警系统，在配置文件里 grep 不到 webhook，判定「告警发不出去」。这个结论**可复现，但错误**——webhook 配在另一个文件，脚本头部注释写得清清楚楚，告警一直正常。
- 一次「验证通过」只检查了 HTTP 状态码——而两种完全不同的失败原因返回同一个 401，看起来一模一样。这个"通过"什么也没验证，只是复述了状态码。

**可复现 ≠ 正确**：一个查错了对象的检查，会稳定地给出错误答案。

我们自己是这么干的，也希望你合得来：

- 拿到结论先问「怎么验证」，而不是「听起来有道理」
- 验**链路通不通**，而不是验**文件里有没有某一行**
- 断言带具体数字和实际输出（"缺字警告 0 条"），而不是形容词（"应该没问题"）
- 搞砸了直说——**这里不会因为报告失败追责，藏着才会出事**

## 核心能力（二）：给 AI 定方向，以及否决它

验证是被动的——它只能拦住已经写出来的错东西。这个岗位还有主动的一半：**决定该往哪走，以及在 AI 交出"能跑，但不该这么做"的方案时否决它。**

AI 很擅长给出**可行**的方案。但它默认挑最省事的路，通常算不进三件事：**改动的波及面、安全边界、三个月后谁来维护。** 同样是这个项目上的真事：

- **端口冲突**：某个服务和用户容器抢端口。AI 的方案是把那个服务挪走——技术上没错，但要连带改四处配置和线上环境变量。实际采用的是让端口分配器认识宿主上的真实占用：一次改动，将来撞上任何新组件都能自动躲开。
- **内部探针**：宿主进程需要知道某个容器"还有没有活在跑"。最省事的做法是开一个公开接口。但容器之间网络互通，而每个容器里跑的正是能执行任意代码的 agent——公开它等于让用户能互相探对方的活动状态。实际做法是复用已有的本机免鉴权路径，不新增任何对外接口。
- **并发改代码**：同时派多个 AI 修五个缺陷，其中四个都要改同一个文件。按"任务"分给它们必然互相覆盖——得按**文件所有权**重新切分，并且把跨文件的约定（比如统一用哪个字体名）先定死再开工。

共同点：**AI 给的都是能跑的方案，问题是代价没被算进去。** 这部分没法外包给 AI——它需要你对整套系统有判断。

还有一种更难的否决：**判断某件事根本不需要做。** 比 AI 多写一个功能更有价值的，往往是拦住一个不该加的功能。

## 技术栈

| 层 | 技术 |
|---|---|
| 入口 | Caddy（自动 HTTPS、安全响应头、SSE 不缓冲） |
| 编排 | 自研 Node 生命周期管理器（按需启停、路径路由、并发上限） |
| 运行时 | Docker + docker compose，每用户独立容器与数据卷 |
| 应用 | Node 网关 + OpenCode（AI agent 运行时）+ 科研技能包 |
| 模型 | 自建 LLM 网关 → DeepSeek，按用户档位路由 |
| 文档产出 | pandoc + XeLaTeX（中文排版）、matplotlib（科研作图） |
| 运维 | systemd、cron、企业微信告警、卷备份 |

不要求入职时全部掌握。基础扎实的人借助 AI，两周内能上手这套栈——我们真正在意的是上一节（怎么验证 AI 给的东西）。

## 面试方式

两份材料，对应上面两项核心能力：

1. **一份真实的故障分析报告**——请你评估它的结论，说明你会怎么验证。
2. **一个 AI 给出的改造方案**——它能跑。请你判断值不值得这么做；如果不值得，你会怎么做。

**我们看的是你的判断过程，不是当场答对。** 说"我不确定，我会这样验"完全可以——我们自己日常就是这么干的。材料提前发给你，聊的时候一起过，不搞突击。

第二轮看脱敏后的架构材料与代码片段，聊你会先动哪里、以及**你觉得哪里当初就不该那么做**。
