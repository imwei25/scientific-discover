# 方案设计：打包版接入微信 / 企微 / 聊天工具（产品化）

> 2026-08-13。前置阅读：`调研-打包版接入微信企微聊天工具.md`（三条路线 + PoC 全部实测结论）。
> 一句话：**分两阶段。Phase 1 托管 cc-connect + 我方包装器，把 PoC 里手工做的事全部自动化，
> 快速出货；Phase 2 把 agent 侧换成"网关 shim"，让聊天会话走产品正门（进界面、进侧栏、配额对账）。**
> 不推荐上来就自研平台协议（原路线 B）——协议维护量大且 cc-connect（MIT）已把 10+ 平台养熟。

---

## 一、PoC 已钉死的事实（设计的地基）

1. cc-connect 原生驱动打包版内置 opencode 1.17.14 可行；LLM 走 27821/cloud/v1 转发，计费配额照走。
2. 技能、多轮、交互式反问、`.venv` 出图、图片/文件回传（`cc-connect send`）全部跑通。
3. 中间事件（reasoning/tool）cc-connect 无条件转发、无开关 → 我方包装器 `oc-wrap.mjs` 在
   `cmd` 层过滤已实测解决；**转发策略从此归我方控制**——这也是整个产品化的支点。
4. 已知毛边（产品化必须内置兜住）：`cmd` 空格拆分、`/bind setup` 写 OPENCODE.md 而 1.17.14
   只认 AGENTS.md、agent PATH 需含 cc-connect、规则文件只在新会话生效、npm 首装走 GitHub 会被重置。
5. 企微智能机器人：WebSocket 免公网 IP，限速 30 条/分（过滤后单轮 1–2 条，安全）。
   微信个人号（ilink，官方接口）：文档载明支持文件/图片双向，**未实测**。

## 二、选型结论

| | Phase 1（托管 cc-connect） | Phase 2（网关 shim） | 原路线 B（自研协议，搁置） |
|---|---|---|---|
| 平台协议 | cc-connect 维护 | cc-connect 维护 | 我方维护（不划算） |
| 会话进产品界面 | ❌（独立于界面） | ✅ | ✅ |
| 配额/产物一致性 | 计费对、界面对不上号 | 全对 | 全对 |
| 工作量 | ~1 周 | +~1 周 | ~3 周起 + 长期维护 |

**Phase 1 先出货的理由**：用户价值（手机上使唤科研 agent）不依赖"会话进界面"；
先让真实用户用起来，Phase 2 的优先级让数据说话。

## 三、Phase 1 设计：托管 cc-connect

### 3.1 打包与布局

- `bundle\runtime\cc-connect\cc-connect.exe`：安装包预置二进制（MIT，~10MB；bundle.ps1 下载钉版本
  **v1.4.1** 并校验哈希——npm 首装在线拉 GitHub 会被重置，绝不能让用户端现场下载）。
- `bundle\app\chat-bridge\`：`config.toml`（生成）、`oc-wrap.mjs`（随包）、`agents-template.md`
  （发文件说明书模板，即 PoC 里 /bind setup 那份的定制版）、`bridge.log`。
- 升级 cc-connect 版本 = 换二进制 + 跑冒烟（见 3.6），**版本钉死**，不自动升级。

### 3.2 网关新模块 `web/chat-bridge.mjs`

职责四件：

1. **配置生成**：从进程 env（同 headless-env.json 来源）拼 `config.toml`：
   - `cmd = "<node.exe> <oc-wrap.mjs>"`——**所有路径经无空格 junction**
     （`bundle\app\chat-bridge\bin\` 下建 junction 指向 runtime，装机时由安装器或首启创建；
     彻底绕开 `cmd` 空格拆分坑）；
   - env 全套注入（OPENCODE_CONFIG / XDG_CONFIG_HOME / PATH 含 cc-connect 目录 / .venv…），
     剥 `\\?\` 前缀；
   - `admin_from` 默认**空**（全部特权命令禁用）；`allow_from` 见 3.5。
2. **work_dir 策略**：每个聊天对端一个目录 `outputs\chat_<platform>_<peerhash>\`，
   建目录时写入 `AGENTS.md`（发文件说明书模板）——**不依赖 /bind setup**，
   也就不吃 OPENCODE.md 文件名坑；opencode 换版本后若认了 OPENCODE.md 也不冲突。
3. **生命周期**：用户开启且（云端已登录或自设 API 就绪）→ spawn `cc-connect --config <path>`；
   app 退出 → 随网关的 taskkill 进程树一起死（挂在网关子进程下）；崩溃退避重启（3 次封顶，
   状态报给界面）。**网关重启（token 轮换）后**：桥不用动——包装器每次 spawn 的 opencode
   都重读 opencode.json（PoC 已验证），只有跨重启的**进行中**会话会断，桥收到错误时对该
   会话发 `/new` 级别的重建即可。
4. **状态与设置 API**：`GET/POST /api/chat-bridge/config`（bot_id/secret、开关、绑定列表）、
   `GET /api/chat-bridge/status`（连接态、最近错误）、微信扫码流（见 3.4）。

### 3.3 包装器 `oc-wrap.mjs` 进化（PoC 版 → 产品版）

PoC 版只做过滤（丢 reasoning/tool）。产品版加三件：

1. **进度聚合**：长任务每 ≥30s 把积累的 tool 概要压成一条「⏳ 正在：跑统计脚本…」推送
   （直接调 `cc-connect send -m`，绕过事件流），远低于 30 条/分限速；
2. **产物兜底**：`step_finish reason=stop` 时扫 work_dir 新文件（mtime 快照对比，
   同调研文档 5.1 的约定输出目录思路），模型忘了调 `cc-connect send` 也能把交付物送到；
   大于 50MB 提示改用界面下载；
3. **敏感兜底**：出站文本过一遍脱敏白名单（正则级，非完整 deidentify）——聊天平台是外发通道，
   患者数据不应该出现在微信里；命中即替换并附提醒。

### 3.4 设置界面（打包版 Web UI 新页「聊天接入」）

- 企微：填 bot_id / bot_secret（管理后台建智能机器人的图文引导内嵌）→ 保存即拉起桥 →
  状态灯（已连接/重连中/凭证错误）。
- 微信个人号：点「扫码绑定」→ 网关驱动 `cc-connect weixin setup` 捕获二维码
  → 渲染到界面 → 扫码成功回写 token（**Phase 1.5，待 ilink 通道实测后再放开**）。
- 通用：总开关；绑定成员管理（allow_from 列表，展示企微昵称）；「长任务进度提示」开关；
  凭证存 `chat-bridge/config.toml`，纳入卸载清理闸（同 cloud-state.json 待遇）。

### 3.5 安全默认值（不可妥协项）

- `allow_from` **默认拒绝所有人**：首次连接后，第一个向机器人发消息的成员进入"待批准"，
  在设置界面点头才生效（防止企业里任何同事都能驱动用户机器上的 agent）；
- `admin_from` 永远为空——`/shell` `/dir` 等特权命令在产品形态下没有存在理由；
- 群聊默认不响应（仅单聊），开群聊需显式打开并逐群批准；
- 桥只监听本机 api.sock；出站敏感兜底见 3.3。

### 3.6 冒烟与回归

打包 CI 加一条链路测试（复用 PoC 脚本思路）：起网关 → 起桥（mock 平台或 cc-connect 的
本地测试模式）→ 注入一条消息 → 断言：spawn 的 opencode 事件流无 reasoning/tool、
work_dir 产物被登记、`cc-connect send` 可达。cc-connect 换版本必跑。

## 四、Phase 2 设计：网关 shim（会话进产品正门）

把 `cmd` 从「包装真 opencode」换成「伪 opencode CLI」：

- shim 实现 `run --format json`：内部转 `POST /api/chat/start` + SSE `/api/chat/attach`，
  把网关事件流翻译回 opencode JSONL surface（只需 step_start / text / step_finish 三种）；
- 会话从此走产品正门：进会话列表、产物进侧栏（ws_ 目录）、配额界面对得上、
  文件走 file registry 下载链（微信里发短链接而非传文件也成为可选项）；
- 兼容点（PoC 源码已探明）：`session list/delete --format json` 需模拟（映射网关会话）；
  cc-connect 读 opencode SQLite 做消息计数——降级无害，验证即可；
- 包装器 3.3 的三件套原样保留（聚合/兜底/脱敏挪进 shim）。

Phase 1 → 2 用户无感（换 `cmd` 一行 + shim 文件），无迁移成本。

## 六、开放问题（按优先级）

1. 微信个人号 ilink 限额/稳定性未实测（文档载明支持文件双向）——Phase 1.5 用真机扫码验证后再对用户开放；
2. 多用户企业里同一 bot 只有 1 条长连接：一人一机一 bot，引导文案要写清；
3. cc-connect 上游演进（事件 schema、cmd 拆分行为）：钉版本 + 冒烟兜底，必要时 fork（MIT 允许）；
4. 手机端发起的长任务如何中断：Phase 1 提供 `/stop`（cc-connect 现成）；Phase 2 归并到界面的中断按钮。
