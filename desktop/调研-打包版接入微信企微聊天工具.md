# 调研：打包版能否经 cc-connect 等项目接到微信 / 企业微信

> 2026-08-13，基于 feat/auth-gateway @ a84e432c 的代码 + cc-connect v1.4.1 的公开文档与源码。
> 结论先行：**能接，而且比预想顺**——cc-connect 原生带 OpenCode 适配器，打包版的内置
> opencode.exe 可以被它直接驱动；LLM 通道、技能、Python 环境全都能复用。有两条路线，
> 差别在"集成深度"：路线 A 十几分钟能跑通验证，路线 B 才是产品化形态。

---

## 一、cc-connect 是什么

[chenhg5/cc-connect](https://github.com/chenhg5/cc-connect)，Go 写的本地桥接器，14.9k star，MIT。
一头接聊天平台，一头 spawn 本地 agent CLI，消息进、回复出。

**平台侧**（与我们相关的）：

| 平台 | 接入方式 | 公网 IP | 说明 |
|---|---|---|---|
| 企业微信 | 「智能机器人」+ WebSocket 长连接 | 不需要 | 免加解密、免 IP 白名单；限速 30 条/分、1000 条/时；一个机器人只允许 1 条长连接 |
| 微信个人号 | 腾讯官方 ilink 机器人网关，HTTP 长轮询 | 不需要 | `cc-connect weixin setup` 扫码即得 token；**官方接口、非逆向协议**，文字/图片/文件/视频均可收发（语音还能转写） |
| 飞书 / 钉钉 / Slack / Telegram / Discord / QQ | WS / Stream / Socket Mode 等 | 均不需要 | — |

**agent 侧**：`[projects.agent] type = "opencode"` 是内置适配器（`agent/opencode/opencode.go`），
机制是 spawn `opencode run --format json`，逐行解析 JSON 事件流；会话用 `opencode session list/delete`
管理，多轮上下文靠 opencode 自身会话，闲置 30 分钟自动换新会话。关键 options：

```toml
[[projects]]
name = "sci"
admin_from = "你的ilink用户ID"        # 特权命令（/dir /shell 等）白名单，不设=全禁
[projects.agent]
type = "opencode"
[projects.agent.options]
cmd = "C:/Users/<u>/AppData/Local/Niuma Science/bundle/runtime/opencode/opencode.exe"
work_dir = "…/bundle/app/outputs/wechat"   # 在 bundle/app 之下，AGENTS.md 路由才会被向上找到
model = "custom/<模型名>"
[projects.agent.options.env]               # 环境变量可整套注入
OPENCODE_CONFIG = "…/bundle/app/opencode.json"
XDG_CONFIG_HOME = "…/bundle/app/.ocglobal"
# …PATH 前插 .venv/git/pandoc 等，headless-env.json 里有现成快照
```

Windows：基本功能支持（其文档明确默认 shell 是 powershell.exe），npm 可装；
只有 `run_as_user` 用户隔离是 Linux/macOS 专属——单人桌面场景用不上，无碍。

## 二、打包版这边的三个可对接面

（架构细节见探索结论；壳 → node 网关(27821, 0.0.0.0, localhost 免鉴权) → `opencode serve`(27822)）

1. **网关 HTTP API（产品的正门）**：`POST /api/chat/start`、SSE `/api/chat/attach`、
   `/api/upload`、`/api/download`、`/api/outputs`…… 同机调用免鉴权。走这里 = 会话进界面、
   产物进侧栏、配额/模块照常管。
2. **内置 opencode.exe 直接 headless 跑**（cc-connect 用的就是这个面）：官方 1.17.14 未改包，
   `opencode run` 可用。**LLM 通道可复用的关键**：网关每次启动把
   `provider.baseURL=127.0.0.1:27821/cloud/v1 + apiKey=CLOUD_LOCAL_TOKEN(每进程一新)` 写进磁盘
   `bundle/app/opencode.json`（server.mjs:124 writeOcProvider），opencode 是**启动时读文件**——
   所以只要桌面 app 开着，任何时刻新 spawn 的 opencode 拿到的都是当前有效 token，计费/配额
   照走 `/cloud` 转发那套，服务器侧无感。技能与插件靠 `XDG_CONFIG_HOME=.ocglobal` 一并生效。
3. **无头运行器** `web/headless-run.mjs`：复用或自起网关跑任务 JSON。`headless-env.json`
   是壳写的完整 env 快照——路线 A 生成 cc-connect 配置时直接从这里抄 env，不用手拼。

## 三、路线对比

### 路线 A：cc-connect 直驱内置 opencode（验证用，十几分钟）

`npm i -g cc-connect` → 写上面那份 config.toml（env 从 headless-env.json 抄）→
`cc-connect weixin setup` 扫码（或企微建智能机器人填 bot_id/secret）→ 跑起来。

- ✅ 零改我方代码；微信/企微/飞书/钉钉全家桶立刻可用；文件收发（`cc-connect send --file`，上限 50 MiB）、语音转写都是现成的。
- ⚠️ 局限：
  - **必须桌面 app 同时开着**（LLM 走 27821 转发；app 重启 → token 轮换 → cc-connect 手里跨重启的旧会话作废，闲置换会话机制能自愈，但正在进行的长会话会断）。
  - **绕过了网关的会话管理**：微信里发起的会话不进产品界面、产物不进侧栏、不吃 ws_ 目录约定；配额虽照扣但界面上对不上号。
  - AGENTS.md 路由依赖 work_dir 放在 bundle/app 之下（向上查找）；`opencode run` 的会话建立在个别版本有坑（[#28407](https://github.com/anomalyco/opencode/issues/28407)），1.17.14 需实测。
  - 用户要自己装 Node/npm、手写 TOML——对我们的目标用户（医生科研人员）不现实，只适合我们自己验证。

### 路线 B：产品化——桥接到网关 API（推荐的终态）

写一个小桥（node，估 300–500 行，可打进 bundle）：企微智能机器人 WebSocket / 微信 ilink
长轮询 ←→ 网关 `POST /api/chat/start` + SSE 聚合回复 + `file_output` 转企微素材上传。
配置放进现有设置界面（填 bot_id/secret 或扫码），壳/网关管生命周期。

- ✅ 会话进界面、产物进侧栏、配额对得上；用户零门槛开箱即用；不依赖第三方进程存活。
- ⚠️ 工作量真实存在：企微 WS 协议 + ilink 协议要自己实现（可参考 cc-connect 的 Go 源码，MIT 允许移植）；消息聚合策略（agent 跑几分钟，中间工具事件怎么在微信里呈现）要设计。
- 折中变体 B'：**把 cc-connect 二进制打进 bundle**，网关生成它的 config.toml 并托管其生命周期——协议维护外包给 14.9k star 的社区项目，我方只写"配置生成 + 进程管理"，但集成深度同路线 A（会话仍不进界面）。

### 安全红线（两条路线都适用）

微信消息 = 在用户机器上执行任意命令的入口。必须：`allow_from` 白名单锁死发件人（ilink 用户 ID / 企微成员）、`admin_from` 不给或只给机主、群聊场景默认不接。企微智能机器人一个 bot 一条长连接 → 一台机器一个 bot，多用户各建各的。

## 四、PoC 实测结果（2026-08-13，路线 A，企微智能机器人）

**端到端跑通**：企微单聊发消息 → cc-connect(v1.4.1, Windows) → 打包版内置 opencode.exe 1.17.14
（headless `opencode run --format json`）→ LLM 经桌面 app 27821 `/cloud/v1` 转发 →
回复发回企微，全程约 7 秒。配置在 `~/.cc-connect/config.toml`。

验证点与踩坑：

1. **`opencode run` 独立跑没坑**：会话正常创建（#28407 不影响 1.17.14），技能与 AGENTS.md
   全量加载（单轮 21k 输入 token，与界面内一致），计费配额照走云端转发。
2. **cc-connect 把 `cmd` 按空格拆分**——安装路径 `Niuma Science` 含空格会被截断成
   `C:\...\Niuma`。解法：建无空格 junction（`~\.cc-connect\oc-bin` → `bundle\runtime\opencode`），
   `cmd` 指向 junction 内的 exe。产品化若托管 cc-connect，此坑必须内置处理。
3. **二进制下载**：npm 包首跑时从 GitHub Releases 拉 exe，国内 ECONNRESET 后自动回退
   Gitee 镜像成功——离线/内网环境需预置二进制。
4. cc-connect 首跑会往 config.toml 里回写默认项（如 `language`），配置生成器要容忍它改文件。
5. 环境变量整套注入（OPENCODE_CONFIG / XDG_CONFIG_HOME / PATH / .venv 等）从
   `web/headless-env.json` 抄即可，注意剥掉 `\\?\` 长路径前缀。

深测（同日）——**技能、多轮、文件回传全部跑通**，又暴露 4 个问题（均已定位）：

6. **真实技能任务 ✅**：企微里说「画一个正弦函数曲线发给我」正确触发 `nature-figure` 技能，
   中途技能反问「Python or R?」经企微一来一回完成（交互式技能对话可用），.venv 出
   300 DPI PNG + SVG 落在 work_dir。多轮消息续接同一 agent 会话。
7. **长任务打爆企微限速 ❌→✅已解**：cc-connect 把中间过程逐条推送，1 分 42 秒的任务发了
   十几条，撞死智能机器人频率限制（errcode 846607）后大量消息（含最终回复）丢失，
   **且没有关闭中间推送的配置**（源码确认 `agent/opencode/session.go` 无条件转发
   text/reasoning/tool 事件）。
8. **模型思考过程外泄 ❌→✅已解**：doubao 的 reasoning 文本被当正式消息推送到企微。
   **7、8 的解法（已实测）——事件流包装器**：利用 `cmd` 按空格拆分的特性，
   `cmd = 'node.exe ~\.cc-connect\oc-wrap.mjs'`，包装器透传真 opencode 并过滤 run 的
   JSONL 输出：丢弃 `reasoning` 与 `tool` 事件，其余子命令原样透传。生产验证：余弦曲线
   任务 90 秒，企微端只收到一条正文 + 一张图，零限速错误。副作用（无害）：cc-connect 日志
   `tools=0`、报 slow agent first event；长任务期间用户端静默（要进度提示得在包装器里做
   节流聚合——产品化的活）。包装器同时是路线 B' 的雏形：转发策略完全归我方控制。
9. **文件回传要三个前提才通**（缺一不可，已实测全通）：
   ① 聊天里执行一次 `/bind setup`——cc-connect 往 work_dir 写指令文件教 agent 用
   `cc-connect send --image/--file`；**但它写的是 `OPENCODE.md`，opencode 1.17.14 不认**，
   要复制成 `AGENTS.md` 才会加载（实测确认；新版 opencode 可能已支持，产品化时按版本适配）；
   ② agent 的 PATH 里要有 cc-connect（npm 全局目录，如 `C:\nvm4w\nodejs`）；
   ③ `/new` 重开会话让指令生效（规则文件只在会话创建时加载）。
   三者齐备后 agent 正确执行 `cc-connect send --image …`，图片直达企微。
10. `admin_from` 填企微用户 ID（`message received` 日志里 `user=` 字段）后 `/bind`、`/new`
   等命令可用。

仍未验证：桌面 app 重启后 token 轮换的自愈表现（预期闲置换会话可自愈，未实测）；
微信个人号（ilink）通道。

## 五、建议

1. 先按路线 A 在自己机器上跑通一次端到端（企微智能机器人最省事，不用动个人微信），验证 1.17.14 的 `opencode run` + 我们的 opencode.json/技能链路无坑；
2. 验证通过后决定产品化走 B 还是 B'（差别 = 自研协议 vs 托管 cc-connect）；
3. 微信个人号 ilink 是新东西，限额、稳定性、开通门槛需在 A 阶段实测后再决定是否对用户开放。
