# 桌面本地部署方案说明：本地端 / 云服务器端职责划分（与原云端多用户方案对比）

> 分支 `feat/desktop-windows`，2026-07-28。适用对象：给客户做本地部署（一键安装 exe）的产品形态。
> 一句话：**算力编排与数据全部下沉到客户电脑，云端收缩成"鉴权 + token 管控"的瘦网关；
> 鉴权仍在云端，用户管理从云端移交给本地端。**

---

## 一、两种形态一览

```
【原方案：云端多用户 SaaS】                【新方案：本地桌面版 + 云端瘦网关】

 浏览器(用户A/B/C…)                        客户电脑（安装 exe）
    │ https                                  ┌────────────────────────────┐
 Caddy + DuckDNS 子域/用户                    │ Tauri 壳(窗口+进程管理)      │
    │                                        │  └ node 网关 server.mjs     │
 manager.mjs（生命周期/登录门户/验证码/       │      └ opencode + 23技能     │
   按需容器/额度上报/模块授权/档位）           │      └ 嵌入式Python科研栈    │
    │                                        │  数据/会话/产物 全在本机      │
 每用户一个 Docker 容器                       └──────────┬─────────────────┘
   (opencode+网关+技能+Python)                           │ 仅 LLM 请求(https)
    │                                                    ▼
 one-api（LLM 多渠道调度/额度）                云端：鉴权 + one-api(按key管
    │                                              额度/计费/停用) ＋ 上游LLM
 上游 LLM(DeepSeek 等)
```

两套形态**共用同一份代码**（web/server.mjs 网关本就有 Windows 分支、技能零改动），不是两个产品分叉；
桌面版只是把"容器"换成了"客户机上的便携运行时"。

## 二、新方案职责划分

### 本地端（客户电脑，安装包内）负责

| 职责 | 具体内容 | 现状 |
|---|---|---|
| **全部算力执行** | opencode agent 循环、23 个技能、统计/作图/排版（嵌入式 Python 3.12 + pandoc + Git Bash） | ✅ 已实现 |
| **数据存续** | 上传文件、会话历史、产物（outputs/）、患者数据脱敏前后文件——**全部只存客户本机** | ✅ 已实现 |
| **用户管理**（从云端移交） | 谁能打开/使用这台机器上的应用：本机 localhost 免密；局域网访问走本地账号密码（LAN_USER/LAN_PASSWORD，界面可改密）；会话/产物的增删由客户自己管 | ✅ 单账号版已实现 |
| | 本地多账号/多角色（同一诊所几个人分账号用一台机） | ⬜ 未做，需求出现再加 |
| **运行时自治** | 开机拉起、端口自清、进程树回收、崩溃后重启自愈（server.mjs 原有逻辑） | ✅ 已实现 |
| **凭据保管** | 云端发的接入 key 存本机（cloud.json 或界面模型设置） | ✅ 已实现（明文落盘，后续可换短时 token） |

### 云服务器端负责（收缩后）

| 职责 | 具体内容 | 现状 |
|---|---|---|
| **鉴权**（保留在云端） | 客户端每次 LLM 调用都带 key，one-api 验 key 放行/拒绝——**key 无效 = 整个产品立即不可用**，这就是续费/停用抓手（kill switch） | ✅ one-api 现成 |
| **token 管控** | 按 key 记量、限额度（日/总）、计费依据导出 | ✅ one-api 现成 |
| **多渠道调度** | 上游 LLM 的渠道管理/failover/换模型，客户端无感 | ✅ one-api 现成 |
| **客户粒度管理** | 发 key、停 key、调额度——云端管到**客户（一个 key）**为止，客户内部谁在用不归云端管 | ✅ one-api 现成 |
| **用户身份与分级** | 手机号验证码 / 微信扫码登录，云端维护用户表（身份+档位+额度），登录时下发**有效期内有效的 key**（详见 §六） | ⬜ 已定设计，待实现 |
| 版本/技能更新分发 | tauri-updater + 技能包从云端拉 | ⬜ 后续 |

**关键转变**：云端不再托管用户的**运行环境与数据**（原方案每人一个容器），但**仍然认识每个用户**——
手机号/微信登录后，云端维护"用户身份 → 档位 → 额度"的映射（否则没法分级管理，见 §六）。
移交给本地端的是：运行环境、数据存续、以及"这台机器谁能碰"的门禁；留在云端的是：身份、分级、计量、停用。

## 三、与原方案逐项对比

| 维度 | 原方案（云端多用户） | 新方案（桌面本地部署） |
|---|---|---|
| **鉴权** | 云端：manager 登录门户+验证码+HMAC cookie，per-user 容器隔离 | **仍在云端**，但对象变了：验的是"这个客户的 key 还有效吗"（one-api），而非"这个人是谁" |
| **用户管理** | 云端：users/*.env 账号体系、模块/技能授权、档位（tiers.env）、管理台 | **落到本地端**：本地账号密码、局域网访问控制、会话数据管理都在客户机上；云端不再维护最终用户名单 |
| **算力成本** | 服务器出：容器内存/CPU 是我们的（WARM_CAP、OOM 都是我们的事） | 客户出：跑在客户电脑上，服务器只剩转发 LLM 的带宽 |
| **数据位置** | 服务器上（uploads/outputs 卷），要备份、要对客户承诺安全 | **客户本机**——患者数据不出院/不出单位，是本方案最硬的卖点；但要说清"脱敏后文本会进云端 LLM" |
| **额度/计费** | manager 每日 USD 额度 + one-api 双层 | 只剩 one-api 一层（按 key），本地网关的日额度逻辑仍在、可选用 |
| **模块/技能授权** | 管理台按用户开关模块、受限技能物理隔离 | v1 全量打包；按客户裁剪 = 打包时少 COPY（bundle.ps1 加过滤即可），无运行时授权面板 |
| **更新** | 服务器重建镜像，一次全员生效 | 每台客户机各自装新包（后续 tauri-updater 自动化）；**版本碎片化是新增成本** |
| **隔离模型** | 一人一容器（内核级），只读挂载保护技能 | 一客户一台机，天然物理隔离；但**技能明文在客户手里**（IP 裸奔，护城河=云端 key+持续更新） |
| **故障责任** | 全在我们（容器 OOM、磁盘、积压） | 分家：本机跑不动/装不上是现场问题（smoke.sh 可诊断），LLM 不通才是我们的 |
| **PDF/预览能力** | 容器内 texlive+LibreOffice 全量 | 降级：PDF 排版需客户机装 MiKTeX、pptx 在线预览需 LibreOffice（装上自动恢复），其余完整 |
| **离线** | 不存在此概念 | 不能离线：LLM 与文献检索都要网；断网时本地界面能开、无法生成 |

## 四、鉴权与用户管理的落位设计（回应"鉴权云端、用户管理本地"）

**鉴权留云端的理由**：它是商业控制点。放本地的任何校验都可被客户绕过（代码在人家机器上）；
只有"每次 LLM 调用都要过云端 one-api 验 key"这一道是绕不开的——不交钱→停 key→产品失能。
因此鉴权的**唯一可信执行点**是云端网关，本地端只做凭据的保管与转交。

**云端与本地各管用户的哪一半**：云端管**身份与商务**（这个手机号/微信是谁、什么档位、用了多少、
是否停用）——没有这一半就没法分级管理和计费；本地管**数据与门禁**（这台机器上的会话/文件、
局域网谁能访问）。云端认识用户但**不碰用户的内容数据**，合规责任边界依然清晰。
本地网关现成的账号密码/改密/localhost 免密机制即是 v1 的本地门禁。

**边界情况**：
- **key 泄露/外借**：one-api 侧按 key 限额 + 看用量突刺；必要时换 key 重发（客户端改一处配置）。
- **一客户多台机**：同一 key 多机共用（额度合并计），或一机一 key（可分机停用）——发 key 策略问题，技术上都支持。
- **合规口径**：宣传"数据不出本地"时必须写明"提交给 AI 分析的内容（含脱敏后文本）会发送至云端模型"；
  含患者数据的分析先走 deidentify 是产品内置流程，但要在说明书里写成客户义务。

## 五、后续：手机号/微信登录 + 有效期 key（已定设计，待实现）

目标：云端知道**每个用户**是谁（分级管理的前提），登录时给本地端发一个**有效期内有效的 key**，
有效期内下次启动免登录直达。

### 登录与 key 生命周期

```
首次注册/登录                                    日常启动
─────────────                                   ─────────
桌面端开登录页 ──手机号+验证码──▶ 云端 auth        桌面端读本地缓存的 key
        （或微信扫码，回调到云端）    │              │
                                    ▼              ├─ 未过期 → 直接进主界面（免登录）
                    验身份 → 查/建用户记录          │           后台静默续期（剩余<N天时换新key）
                    （手机号/openid + 档位 + 额度）  │
                                    │              └─ 过期/被停/401 → 弹回登录页
                                    ▼
                    在 one-api 上为该用户创建/轮换 token
                    （设 expired_time=有效期、quota=档位额度、模型走档位）
                                    │
                                    ▼
                    下发 { key, baseURL, model, tier, expiresAt }
                                    │
                    本地端存起来（现 cloud.json 位置）→ 之后所有 LLM 调用带此 key
```

### 设计要点（尽量复用现有设施）

1. **"有效期内有效的 key" = one-api token 本身**。one-api 的 token 原生支持过期时间与额度上限，
   云端 auth 服务登录成功后调 one-api 管理 API 建/换 token 即可——不用自造一套 JWT+校验中间件，
   LLM 网关侧零改动（验 key 的还是 one-api）。
2. **分级管理挂在用户表上**：云端用户表 `{手机号/openid, 档位, 状态}`；档位决定发 token 时的
   额度与可用模型（对齐现有 tiers.env 的档位定义），登录响应把 `model` 一并下发，本地端写进
   模型配置。调档 = 改用户表 + 下次续期生效（或主动踢 token 立即生效）。
3. **免登录 = key 未过期**：本地只判断缓存 key 的 expiresAt；剩余不足 N 天（如 3 天）时启动后
   静默调续期接口换新 key，用户无感。**停用/欠费 = 云端删 token**，下一次 LLM 调用即 401，
   本地端捕获后弹回登录页——kill switch 从"停客户"细化到"停个人"。
4. **验证码通道**：手机号短信需企业实名 + 签名/模板审核（阿里云/腾讯云 SMS 皆可）；
   **微信扫码登录需微信开放平台"网站应用"资质（企业主体认证）**，个人主体办不下来——
   故落地顺序建议：先手机号验证码（门槛低、覆盖全），微信扫码作二期。
5. **一人多机**：同一身份多台机器登录 → 共用同一 token（额度合并计），或每设备一 token
   （可单独踢设备）——用户表加设备维度即可，先按共用做。
6. **安全边界**：key 仍会落客户盘（这是本地部署的固有属性），防滥用靠"有效期短 + 额度上限 +
   用量突刺告警 + 随时可踢"，不靠藏得住。

### 云端需要新增的组件

| 组件 | 职责 | 备注 |
|---|---|---|
| auth 服务（可并入 manager.mjs 或独立小服务） | /register /login /renew：验证码收发、微信回调、用户表 CRUD、调 one-api 管理 API 发/换/删 token | 用户表可先 SQLite |
| 短信通道接入 | 验证码下发 | 需企业实名+模板审核，办理周期数天 |
| （二期）微信开放平台应用 | 扫码登录 | 需企业主体认证 |

### 本地端需要新增的改动

- 登录页（Tauri 壳内嵌云端登录 URL 或本地页调云端 API）+ key 缓存/过期判断/静默续期；
- LLM 调用 401 时的"重新登录"引导（现在只会报模型调用失败）。

## 六、v1 交付物与已验证事项（截至 2026-07-28）

- `desktop/bundle.ps1`：组装 1.7GB 自包含目录（便携 node / opencode 1.17.14 / PortableGit /
  pandoc / 嵌入式 Python3.12+科研栈钉版），国内镜像优先。
- `desktop/launcher/`：Tauri2 壳 → NSIS 安装器，per-user 安装免管理员，退出清进程树。
- 已验证：staging 包网关+opencode 全绿；真实 LLM 请求打通（唯一失败为 dev key 余额 402，属账户问题）；
  技能命令契约（`${REPO_ROOT}` 展开 / `.venv/bin/python` / 裸 `python3` / pandoc / heredoc）包内 bash 全绿。
- 客户机要求：Win10/11 x64 + 联网；无需管理员、无需预装（WebView2 缺失时安装器自动装）。
