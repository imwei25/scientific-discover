# ---- 刻意不装 flask / playwright / chromium（ppt-master 的三条网页路径，已实测定论）----
# ppt-master 有三处依赖 flask：Step 4 确认页、Step 6 网页 SVG 编辑器、以及 visual_review.py
# （AI 逐页看图自查）。这三条在本部署里全部不装，理由是实测出来的，不是猜的：
#   ① 前两条面向【用户】，但服务绑的是【容器内】127.0.0.1:5050，而容器只对外发布 3000 端口，
#      用户浏览器里的 localhost:5050 指向的是用户自己的电脑 —— 永远打不开。
#      更坏的是 Step 4 确认页若真能启动，AI 会去等一个没人点得到的按钮：每次 --wait 约 590s，
#      三段确认累计最坏 ≈30 分钟纯空等才降级到聊天确认。
#   ② visual_review.py 除 flask 外还需 playwright + chromium（ppt-master 自己的
#      requirements.txt 漏列了 playwright，只在报错信息里提了一句）。轻量的 cairosvg 后端
#      被作者明确否决过，理由是 CJK 渲染成豆腐块 —— 所以 chromium 省不掉。
#      实测体积代价：+1.00 GB（镜像 du -sx / 从 3.16 GB 涨到 4.16 GB）。
#   ③ 而视觉自查是 opt-in：workflows/visual-review.md 原文写明"主流程 Step 1–7 不调用它，
#      只在用户明确要求视觉回看时触发"。为一个用户几乎不会主动要的能力涨 1 GB、并给
#      1400m 的容器再引入一个 300–500MB 级的 OOM 面（已因 LibreOffice 加过串行锁），不划算。
# 对应地，SKILL.md 与 workflows/live-preview.md 里已用「本部署覆盖规则」停用这三条路径，
# 并禁止 AI 向用户播报任何 5050 地址（否则就是给用户一个永远打不开的链接）。
# 将来若要启用：把 flask + playwright 加回本文件，Dockerfile 里补
# `python3 -m playwright install --with-deps chromium`，并给 chromium 加一道类似
# web/server.mjs 里 withSoffice() 的全局串行锁防 OOM，同时撤掉那几处覆盖规则。
# 刻意【不装】 nbconvert（ipynb → md）：它会拖进整个 jupyter 生态
# （nbclient/nbformat/jupyter-core/jupyter-client/pyzmq/bleach/mistune… 十几个传递依赖），
# 而这些传递依赖全都不钉版本——正好和上面给 npm 加 lockfile 追求的可重复构建相反，镜像还要涨几百 MB。
# 镜像里已有 pandoc，`pandoc x.ipynb -o x.md` 同样能转，够用。
# 刻意【不装】的可选项（都不在核心产出路径上，装了平白增大镜像）：
#   edge-tts(旁白配音) / curl_cffi(TLS 指纹绕过) / google-genai(AI 配图) / cairosvg(需系统 cairo)
# 若将来要启用，把对应包加回来即可（ppt-master/requirements.txt 里有完整清单与说明）。
